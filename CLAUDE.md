# horde — Project Conventions

## What this is

Cloud launcher for orc workflows. See SPEC.md for design, ORC_CONTRACT_EXPECTATIONS.md for the orc interface boundary.

## Language & Dependencies

- Go 1.24+, module: `github.com/jorge-barreto/horde`
- CLI: `github.com/urfave/cli/v3`
- SQLite: `modernc.org/sqlite` (pure-Go driver; local run history)
- YAML: `gopkg.in/yaml.v3` (project config)
- AWS (v0.2): `github.com/aws/aws-sdk-go-v2` (DynamoDB, SSM, STS, CloudWatch Logs, S3, ECS)

## Commands

```bash
make build                    # build cmd/horde
make unit-test                # fast Go tests; no Docker, no AWS. What CI runs on every PR.
make integration-test         # real Docker, real horde, real orc (~2 min). CI runs this too.
make vet                      # go vet

# ECS end-to-end tests — real AWS stack, developer-local only (never CI).
# Needs `.env` with AWS_PROFILE + HORDE_E2E_*=1 and a live SSO token.
make e2e-up                   # deploy CDK stack (~5 min cold / ~2 min warm)
make e2e-test                 # run full TestECS_* suite against it (~15 min)
make e2e-down                 # destroy stack (~3 min). ALWAYS run when done.

# Free AWS-backed check (no resources created, no charges).
make bootstrap-validate-test  # ValidateTemplate on rendered CloudFormation
```

## CI

`.github/workflows/ci.yml` runs on every PR to main and every push to main.
Three required jobs: `unit-test`, `integration-test`, `cdk-test`. If any
fails, the PR can't merge. Reproduce locally with the matching `make`
target (or `cd cdk && npm ci && npm run build && npm test` for cdk-test).

## Git

- Commit messages: short and direct. No "Co-Authored-By", "Generated by", or any AI attribution lines.
- Stage specific files — never `git add .` or `git add -A`.

## Code Style

- Standard Go conventions. `gofmt` and `go vet` clean.
- Errors are returned, not panicked. Wrap with context: `fmt.Errorf("loading config: %w", err)`.
- Major interfaces in their own files (`store.go`, `provider.go`). Implementations in separate files (`sqlite.go`, `dynamo.go`, `docker.go`, `dockerimage.go`).
- Tests next to implementation: `foo.go` → `foo_test.go`.
- Never combine `t.Parallel()` with `t.Setenv`, `t.Chdir`, or `os.Setenv` — `testing.T.Setenv` panics on tests with parallel ancestors. If a test needs env mutation, it cannot be parallel.

## Architecture

- `cmd/horde/` — CLI entry point, all commands (launch, retry, status, logs, kill, results, hydrate, list, clean, shell, bootstrap, push, update, version, docs), factory for provider/store (`launch --capacity` selects Fargate Spot vs on-demand).
- `internal/bootstrap/` — CloudFormation template generation + project-slug derivation for `horde bootstrap` (v0.2)
- `internal/provider/` — Provider interface (`provider.go`) + Docker implementation (`docker.go`, `dockerimage.go`); ECS provider in v0.2. ECS launches via `CapacityProviderStrategy` (Spot default; `--capacity` override).
- `internal/store/` — Store interface (`store.go`) + SQLite (`sqlite.go`) and DynamoDB (`dynamo.go`, v0.2) implementations. Both pass shared conformance tests. `Run` carries `Capacity`/`ResumeCount` (Spot auto-resume) alongside `Priority`/`Labels`.
- `internal/config/` — Git remote URL resolution, `.env` file validation, `.horde/config.yaml` project config, SSM parameter loading (v0.2)
- `internal/event/` — run-lifecycle event contract (`Detail`, `DetailFromRun`) + `Emitter` (EventBridge impl + no-op); the Go side of the #36 backbone
- `internal/awscfg/` — AWS SDK config loading, credential diagnostics
- `internal/docs/` — Built-in documentation system (`horde docs <topic>`)
- `internal/runid/` — Run ID generation (12-char alphanumeric via crypto/rand)
- `docker/` — Worker Dockerfile, entrypoint.sh, git-askpass.sh (embedded into binary via `workerfiles.go`)
- `cdk/` — `@horde.io/cdk` npm package: TypeScript CDK construct (`HordeWorker`) + status-sync Lambda. Alternative to `horde bootstrap` for teams with an existing CDK app. Emits the same SSM JSON shape consumed by `internal/config/ssm.go`. (v0.2)
- `worker/` — Optional project-specific Dockerfile extending base image
- `test/integration/` — End-to-end tests against real Docker containers

## Key Design Decisions

- Git is the default identity source — repo URL inferred from the local git remote — but every discovery step is overrideable (flag > env > discovery > error) so programmatic callers (Lambda, CI outside the repo) can run without a checkout. The seam is `config.Resolver` (`internal/config/resolve.go`): `--repo`/`HORDE_REPO_URL`, `--config`/`HORDE_CONFIG_PATH`, `--ssm-path`/`HORDE_SSM_PATH` are root persistent flags (urfave `Sources: cli.EnvVars(...)` folds flag>env; never `Required` per the `--json` rule). `cmd/horde` builds the resolver via `newResolver(cmd)` and threads it through launch/retry/list/clean and the factory (`resolveSSMPath(*config.Resolver)`, carried on `factoryDeps.resolver` via `withResolver`). Any new ECS-reaching call site MUST inject the resolver (`defaultFactoryDeps().withResolver(newResolver(cmd))`) or it silently loses `HORDE_SSM_PATH`/`--ssm-path`/`--repo`.
- The bucket key (the `repo` string partitioning all run history on the DynamoDB by-repo GSI / SQLite repo column) is **canonical**: `config.CanonicalRepo` normalizes the remote, strips a trailing `.git`, and lowercases, so a repo cloned with or without `.git`, via https or ssh, in any case, hashes to one bucket (fixes the dev-clone vs `actions/checkout` split). `config.RepoURL` returns canonical form; `NormalizeRepoURL` is unchanged (still preserves `.git`) and `bootstrap.Slug` already strips `.git`, so both are unaffected. SSM `cfg.Repo` stays the **authority** for ECS — `resolveCanonicalRepo` returns it verbatim even when `--repo` is set, and it is never canonicalized at read time, so existing deployments are not re-partitioned. Canonicalization is forward-only: pre-fix local SQLite rows under a `.git` key are orphaned (local, single-user; S3 artifacts are keyed by run_id, unaffected).
- Optional project config in `.horde/config.yaml` (volume mounts; `secrets:` block declares extra env-var secrets beyond the two canonical `CLAUDE_CODE_OAUTH_TOKEN`/`GIT_TOKEN` — see `horde docs config`); secrets from `.env` file (gitignored) via `docker run --env-file`
- GIT_TOKEN protected via `GIT_ASKPASS` credential helper — never in process args or `.git/config`
- SQLite for local run history (`~/.horde/horde.db`); DynamoDB for shared team history (v0.2)
- Store selection follows provider: docker → SQLite, aws-ecs → DynamoDB
- Run timeout (default 24h) enforced lazily — checked on status/list/results calls, not a background timer
- Provider.Launch returns `*LaunchResult` with `InstanceID` + `Metadata map[string]string` (no provider-specific fields on the generic type)
- User labels (`horde launch --label k=v`) live in `Run.Labels`, a dedicated column/attribute strictly separate from provider-internal `Run.Metadata` (cluster_arn, log_group, …) — set once at launch, never on `RunUpdate`, carried across `retry`. `horde list` filters via `store.ListRuns(RunFilter)` (status set, workflow, ticket, labels AND-exact, started_at range): DynamoDB filters server-side via FilterExpression on the by-repo GSI; SQLite fetches repo rows and applies the shared `matchesFilter` predicate. Status is filtered *after* `Finalize()` since finalize can flip a run terminal mid-call.
- Two-layer Docker image: base (`horde-worker-base:latest`) with orc/claude/tools, project image (`horde-worker:latest`) optionally extends via `worker/Dockerfile`
- Containers preserved after stop/kill for retry and shell access; workspaces persist at `~/.horde/workspaces/<run-id>/`
- Recoverable runs: orc exit 2 → `timed_out`, exit 4 → `rate_limited` (in `mapExitCode`); both are terminal-but-recoverable, distinct from `failed`/`killed`. `horde retry` accepts all four. Status is free-text (no schema migration); `IsTerminal()` and store filters handle them — active filters are `{pending,running}` allowlists. See `horde docs retry`.
- ECS recoverable runs reproduce the Docker on-host-workspace guarantee via S3: Fargate has no persistent FS, so the worker syncs `~/.claude` (agent session) + full `/workspace` (committed + uncommitted + `.git`) to S3 on SIGTERM and restores both on `horde retry` with the same run ID. orc runs backgrounded so SIGTERM reaches it and its interrupt-save finishes before the uploads; orc's true exit code is preserved across the signal. Uses the task role's S3 access — no git push / repo write.
- Fargate Spot by default + auto-resume (aws-ecs): ECS runs launch via a `CapacityProviderStrategy` (NOT `LaunchType` — the two are mutually exclusive in `RunTask`), defaulting to `FARGATE_SPOT`; `horde launch --capacity spot|on-demand` overrides per run (stored on `Run.Capacity`, reused on retry/resume — `horde retry` preserves the stored value). Both providers are always registered on the cluster (free — registration costs nothing; you pay per running task; CDK `enableFargateCapacityProviders`, bootstrap CFN lists both, task def keeps `RequiresCompatibilities: [FARGATE]` which is a compatibility, not a provider). On a Spot interruption the task stops with ECS `stopCode == "TerminationNotice"` (a `horde kill` is `UserInitiated` and never matches); the worker's S3 snapshot (workspace + `~/.claude` + artifacts, already synced on SIGTERM) is the resume source. The TS status Lambda then RE-QUEUES the run (`status=queued`, `priority=highest`, `ResumeCount++`, `REMOVE instance_id`, and **`SET started_at` to the zero-time sentinel `0001-01-01T00:00:00Z`** — NOT removed: `started_at` is the `by-repo` GSI range key, so removing it would drop the run from the index both drainers query and silently lose it; the sentinel is byte-identical to what Go's `--enqueue` path writes) under a `ResumeCount < MAX_RESUMES` budget (default 5, CDK prop `maxSpotResumes`) instead of the terminal write, and emits a **`run.requeued`** event (NOT `run.terminal` — that is a public consumer contract and a re-queued run is not terminal); the drain rule subscribes to `run.terminal` AND `run.requeued`, so the existing drain re-launches it with the same run ID under the concurrency + spend gates. The re-queue is conditional on not-already-terminal so a racing synchronous `horde kill` wins. `Run.ResumeCount`/`Run.Capacity` are additive store fields (SQLite `ensureColumns`, nullable Dynamo attrs) surfaced under `--json`. **CDK-only** (needs the #36 queue/drain; the Python/CFN status Lambda is intentionally not updated — a reclaimed run there lands `killed` for manual `horde retry`).
- Status Lambda records ECS `stop_code`/`stop_reason` into the run's `metadata` map (before the terminal-status guard, so a synchronous `horde kill` still records it). A spot interruption surfaces as `stop_code == "TerminationNotice"`. The CDK (TS) and bootstrap (Python) lambdas are kept in lockstep.
- Per-run token telemetry (`Run.Tokens *store.TokenUsage`: input/output/cache_creation/cache_read + summed `turns`) is read from orc's `costs.json` **first** (it carries token totals on every orc version, flushed per-phase and atomically), with `run-result.json`'s forward token fields as a fallback for once orc promotes them (`provider.ReadTokenUsage`, mirroring the `total_cost_usd` channel; orc-side promotion tracked in jorge-barreto/orc#4). Token counts are lazy/pull-based like cost — written at `Finalize`, never by a background writer. Docker is genuinely lazy-live (`fetchLiveTelemetry` reads the running container's `costs.json` on status/list); ECS reports tokens at finalize (the status Lambdas read `costs.json` from S3 — TS + Python in lockstep, same five attribute names as the Go store consts). In-flight ECS liveness is deliberately deferred. Surfaced under `--json` as a nested `tokens` object on `status`/`list`/`results` and summed into the list `summary` (per `horde docs json`); the orchestrator derives token burn rate client-side from that plus per-run timestamps — there is no `horde burn` command. New SQLite columns are added via the idempotent `ensureColumns` path; new DynamoDB attributes are absent on old items (both → `Tokens == nil`).
- Status detection is lazy: `prov.Finalize()` runs on status/list/results to detect completed/timed-out containers and collect artifacts (a no-op for every terminal status, so terminal ECS runs read from the store and never re-hit live ECS)
- `--json` is a stable machine contract (`cmd/horde/jsonv1.go`, `horde docs json`): under `--json` stdout carries exactly one JSON object, real errors emit an `ErrorV1` envelope on stdout via the root `ExitErrHandler` (human `error:` line stays on stderr), and exit codes are binary (0 for launched/duplicate/capped, 1 for real errors). Do NOT mark a flag `Required: true` on a `--json`-aware command — urfave validates it before the Action and prints help to stdout, bypassing the envelope; validate inside the Action instead.
- Sidecar containers (`HordeWorkerProps.sidecars`, CDK-only — `horde docs cdk`): extra containers added to the worker Fargate task, sharing its network namespace (localhost-reachable) and lifecycle. Construct defaults `essential:false` + logging to the worker log group; reserved name `horde-worker`. Run status is derived from the **worker** container's exit code found BY NAME, never `containers[0]` — because the ECS event's container order isn't guaranteed once sidecars exist. This by-name selection is duplicated in THREE readers that must stay in sync: the TS Lambda (`cdk/src/status-lambda/index.ts`), the Python Lambda (`internal/bootstrap/templates/stack.yaml.tmpl`), and the Go lazy-reconciliation path (`internal/provider/ecs.go::Status`). The worker name `horde-worker` is a cross-language contract (also `internal/provider/ecs.go` const + `cdk` `WORKER_CONTAINER_NAME`); changing it means changing all of them.
- Releases & tag scheme: the repo ships TWO independently-versioned artifacts on DISTINCT tag prefixes (`cmd/horde/release_wiring_test.go` guards the contract; `horde docs install` covers the install/update side):
  - **CLI** (`horde` Go binary) releases on **plain `v*` tags** (e.g. `v0.4.0`). Pushing one fires `.github/workflows/release-cli.yml` → GoReleaser builds the binaries/checksums/GitHub Release and pushes a Homebrew formula to `jorge-barreto/homebrew-tap`. GoReleaser strips the leading `v` natively, so the tag must be plain semver (`monorepo.tag_prefix` is Pro-only — do NOT reintroduce a `cli-v` prefix; it broke validation and asset naming). `make build` stamps the version via `git describe --tags --match 'v*'`.
  - **CDK** (`@horde.io/cdk` npm package) releases on **`cdk-v*` tags**. The tag is only a *trigger* — `npm publish` reads the version from `cdk/package.json`, never the tag. Normally you don't push it by hand: `.github/workflows/tag-on-bump.yml` watches `cdk/package.json` on `main` and auto-pushes `cdk-v<version>` (via `RELEASE_TAG_PAT`, because a `GITHUB_TOKEN`-pushed tag would not fire other workflows) whenever the version bumps, which triggers `.github/workflows/publish.yml`.
  - The two globs are mutually exclusive (`v*` never matches `cdk-v*` and vice versa), so a CLI tag can't trigger an npm publish or vice versa. Historical caveat: the pre-split tags `v0.2.0`–`v0.3.0` were *old CDK* releases under the shared scheme; CLI versioning continues the `v*` number line from `v0.4.0`.
  - **`main` is the release branch.** Feature PRs target `main`, and merging a version bump into `main` *is* the release trigger (`tag-on-bump.yml` watches `cdk/package.json` on `main`; the CLI `v*` tag is pushed against `main`). `main` is therefore always kept releasable. There is no `develop`/staging branch in the release automation — do not assume one.
  - **The version bump MUST ship in the same PR as the change that needs it — never a follow-up PR.** If a PR ships user-facing change, it is incomplete until it also bumps the version of each artifact it touched. A separate "bump the version" PR after merge is a process failure: with `main` as the release branch, the feature can land without ever releasing, and someone has to remember to open a second PR just to move one number. So when finishing any PR that ships user-facing change, add the bump as the final commit (`Release <version>` for CDK; the matching `v<version>` tag is pushed by a human post-merge for the CLI) before requesting review. Only propose deferring the bump if the user explicitly asks; the default is bump-with-the-change.
  - **Bump only the artifact(s) the PR actually touches** — the two versions are independent and need not match. Touching `cmd/horde/`, `internal/`, or `docker/` → **CLI** (`v*`); touching `cdk/` → **CDK** (`@horde.io/cdk`). A CDK-only PR bumps **only** `@horde.io/cdk` and leaves the CLI version untouched (and vice versa); a PR that genuinely changes both bumps both, but they may diverge in number. Do NOT bump an artifact whose code did not change just to keep the numbers aligned — version parity is not a goal.
  - **Semver (pre-1.0):** user-facing features → **minor** (e.g. `0.6.0`→`0.7.0`); bugfixes/docs that ship to users → **patch**. CI-only / test-only / comment-only / internal-refactor changes that ship no user-facing behavior do **not** warrant a bump.
  - **To bump the CDK:** edit `cdk/package.json` `version` + both `version` lines in `cdk/package-lock.json` (top-level and the self-referencing `packages[""]` entry), commit as `Release @horde.io/cdk <version>`. On merge to `main`, `tag-on-bump.yml` auto-pushes `cdk-v<version>` → `publish.yml` runs `npm publish`. **To bump the CLI:** no file edit is needed for the version (GoReleaser/`make build` derive it from `git describe --match 'v*'`); the release is the human pushing the plain `v<version>` tag against the merged commit on `main`.
- Run-lifecycle event backbone + queue (#36, **aws-ecs only**, **CDK-only** — `horde docs queue`/`events`): a custom EventBridge bus (`horde-<slug>`, created by `HordeWorker`) carries `run.started` / `run.terminal` / `run.requeued` / `run.cost-threshold-exceeded` as a stable **versioned** JSON contract in horde vocabulary (never raw ECS shape) — the seam external consumers (and the queue drain) subscribe to. The event SHAPE is the durable artifact: `internal/event` defines it (`Detail`, `DetailFromRun`, `Emitter`, `EventBridgeEmitter`, `NopEmitter`) and the TS Lambdas mirror it. Emission is best-effort and **after** the authoritative store write — store is truth, event is notification-of-truth; a failed PutEvents never reverses state. `run.started` is emitted by whatever transitions a run to `running` (Go CLI on direct launch; the drain Lambda / lazy CLI drain for a drained queued run, since the `--enqueue` CLI has long exited). `run.terminal` is emitted by the status Lambda (`cdk/src/status-lambda/index.ts`) after its terminal write; its `Detail` carries `repo` so the drain can find the backlog. `run.requeued` is emitted by the status Lambda when it re-queues a Spot-interrupted run (see the Spot auto-resume decision above); the drain rule subscribes to both `run.terminal` and `run.requeued`. The Python bootstrap Lambda is **intentionally not** updated (CFN path is being retired; this is CDK-first and CFN never catches up).
- Queue = a `Run` row with `Status: queued` (non-terminal, NOT counted by `CountActive` — it consumes no slot). `horde launch --enqueue [--priority lowest|low|med|high|highest]` parks it (skips the concurrency gate; ECS-only, errors on docker) and returns JSON status `queued` (exit 0, like `capped`/`duplicate`). New fields `EnqueuedAt`/`Priority` on `Run` (additive: SQLite `ensureColumns` + nullable Dynamo attrs; `priority` is a Dynamo reserved word → aliased `#prio`). `StartedAt`/`TimeoutAt` are set at **drain** time, not enqueue (queue-wait is free). Cancelling a queued run → new terminal status `cancelled` (distinct from `killed`: never ran, never cost). `horde queue list|prioritize|cancel` operate the backlog; `queue list` shows drain order. `setOutputs` (test harness) recurses into nested command groups so `queue <sub>` writers reach the test buffer.
- Drain is **mechanical, never judges priority** (the prioritization brain lives above horde — curate via `queue prioritize` / `--force`). Order: highest `Priority` ordinal, then oldest `EnqueuedAt`. Two drainers share one guard: the **TS drain Lambda** (`cdk/src/drain-lambda/`, subscribed to `run.terminal` + `run.requeued`) is primary; the **lazy Go CLI drain** (`cmd/horde/drain.go::lazyDrain`, on `launch --enqueue`/`list`, ECS-only, best-effort, after output) is the missed-event backstop. The double-launch guard is `store.ClaimNextQueued` — an atomic conditional update `queued→pending` (SQLite txn / Dynamo `ConditionExpression`), in the shared Store interface + conformance. A claimed run whose launch then fails → `failed` (NOT re-queued — avoids a poison loop), surfaced in `list`. `FindActiveByTicket` is now `(ticket, workflow)`-scoped (#20) and counts `queued` as a duplicate-blocker.
- Spend-rate cap is **realized-only** (`HordeWorkerProps.maxSpendPerWindow`/`spendWindow` → SSM `max_spend_per_window`/`spend_window`; read by both drainers). Sums `TotalCostUSD` of runs whose `CompletedAt` is in the trailing window; `>=` cap holds the drain (leaves runs queued) and emits `run.cost-threshold-exceeded`. In-flight runs count $0 until they finish, so a burst can overshoot — `MaxConcurrent` is the real blast-radius backstop; live enforcement deferred (#52, needs live telemetry). A held backlog un-holds on window-slide or next CLI touch (no daemon). `HordeWorker` rename to `HordeFleet` is deferred (#53); notifications/external-consumer targets on the bus are deferred (#54).
