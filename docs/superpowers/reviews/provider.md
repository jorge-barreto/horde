# Provider Review

## BLOCKING
None.

## WARNING
- [internal/provider/docker.go:508-524 vs cmd/horde/main.go:1393-1403] All-zero / empty-costs.json presence semantics diverge between the finalize read and the live read of the *same file*. `tokenUsageFromCostsJSON` returns a **non-nil, all-zero** `*store.TokenUsage` whenever the bytes parse as an object — confirmed: `{}`, `null`, and `{"phases":null}` all unmarshal without error and yield `{0,0,0,0, turns:0}`. The live path `fetchLiveTelemetry` reads the identical file but gates non-nil on "at least one field non-zero", so for the same `{}` it returns `nil`. orc flushes costs.json incrementally and writes it early (before the first phase completes), so a run can momentarily have a `{}`/all-zero file. Consequence: the same run can report `tokens: null` while running (status/list) and then `tokens: {input:0,...}` at finalize — and per the store/CLAUDE.md convention "nil = not yet known, zero = known-and-zero", finalize would assert "tokens known to be all zero" for a run that genuinely used tokens but whose costs.json had not yet been populated at the instant Finalize ran. Realistically at finalize the run is terminal and costs.json is fully flushed, so the window is small, but the two readers of the contract's five shared fields should agree on the nil boundary. Consider giving `tokenUsageFromCostsJSON` the same "any-field-non-zero or turns>0" presence gate as `fetchLiveTelemetry` (returning nil for an all-zero parse), so costs.json has one consistent nil semantic everywhere. Note this only affects costs.json; `tokenUsageFromRunResult` already gates on pointer-presence, which is the correct model there.

- [internal/provider/docker.go:553-571] `ReadTokenUsage` opens the door to a costs.json-vs-run-result.json split that `fetchLiveTelemetry` does not have. If costs.json exists but parses to a non-nil all-zero `TokenUsage` (see above), `ReadTokenUsage` returns it and never consults run-result.json's forward token fields — so a future orc that promotes real token totals into run-result.json but still emits an all-zero/`{}` costs.json would be masked. Tied to the same fix: only treat costs.json as authoritative when it actually carries usage. Not blocking because today orc is the single source and costs.json is the live truth, but worth deciding before orc#4 lands.

## NOTE
- [internal/provider/docker.go:766-817] StateUnknown ordering is correct. The audit tree is copied from `workspaceDir/.orc/audit` → `resultsDir/audit` via `copyDir` (recursive, preserves the `<workflow>/<ticket>/` nesting) inside the `os.Stat(workspaceDir) == nil` block, and `run.Tokens = ReadTokenUsage(homeDir, run)` runs after that, reading `LocalResultsDir/audit/<workflow>/<ticket>/costs.json`. Paths line up. When the workspace is gone the copy is skipped and `ReadTokenUsage` simply reads nothing → nil. (One nuance, not introduced by this diff: if a prior Finalize already staged a `LocalResultsDir`, a later StateUnknown read with a vanished workspace would surface the previously-staged costs.json — last-known data, harmless and consistent with the cost field.)

- [internal/provider/docker.go:687,715,764,817] `run.Tokens = ReadTokenUsage(...)` is placed correctly in all four Finalize branches — after every `copyFromContainer`/`copyDir` that populates `LocalResultsDir`, and after the cost read, mirroring the existing `run.TotalCostUSD` placement. The running-completed and stopped branches read from container `docker cp` output; the timeout branch reads after `Stop` (which itself does the best-effort cp); StateUnknown reads after `copyDir`. No branch reads before staging.

- [internal/provider/docker.go:513-516] turns summing is safe for the script-only / phases-absent case. A null or absent `phases` deserializes to a nil slice; ranging over it is a no-op (`turns == 0`), no panic. Confirmed by unmarshal test of `{"phases":null}` and `{}`.

- [internal/provider/docker.go:495-571] Best-effort/nil semantics are correct and consistent with `ReadRunResult`: missing file (`os.ReadFile` err) → skip source; malformed JSON (`json.Unmarshal` err) → nil from `tokenUsageFromCostsJSON` / skip in `ReadTokenUsage`; never returns an error. No resource leaks (no open handles; `os.ReadFile` closes internally). No `%w` wrapping needed since no errors are returned from these helpers — consistent with the surrounding read helpers.

- [internal/provider/docker.go:466-471] The forward token fields on `RunResult` use the same `total_cache_creation_input_tokens` / `total_cache_read_input_tokens` JSON tags as `costsFile` and `liveCosts` in cmd/horde, keeping the five-attribute cross-reader contract aligned. The `Turns *int json:"turns"` on RunResult is a run-total turns field that orc does not write today; if orc ever promotes turns into run-result.json as a per-phase array instead of a scalar (as costs.json does), this fallback would silently read 0 turns. Informational only — tracked by orc#4.

- [internal/provider/docker_test.go:1497-1534, 2444-2520] Test coverage is adequate for the new code: costs.json happy path with turns summed across two phases (1+4=5), missing-file → nil, and run-result.json fallback. Not covered (and would document the WARNING above): an all-zero / `{}` costs.json (asserting whether nil or non-nil zero is intended), and costs.json-present-but-malformed falling through to a valid run-result.json (current code returns nil in that case because the malformed costs.json `os.ReadFile` succeeds but `tokenUsageFromCostsJSON` returns nil, and the code then *does* fall through to run-result.json — worth an explicit test to lock that behavior in).
