# Test Coverage Review

## BLOCKING
- [internal/store/conformance_test.go (whole list-path block, ~808-1419)] No list-path test round-trips a non-nil `Tokens`. `Run.Tokens` is only read back through `GetRun` (CreateGetRun/AllFields line 388, UpdateRun/MultipleFields line 625). `ListByRepo`, `ListRuns`, `FindActiveByTicket`, and `ListActive` each carry their OWN literal SELECT column list (sqlite.go lines 182, 217, 412, 452, 493, 532) feeding the single shared `scanRun`. The five token columns are appended last in every SELECT and last in `scanRun`'s scan order — a pure positional coupling. Because no list path is exercised with token values set, a future edit that reorders/typos the trailing token columns in only ONE SELECT (e.g. swaps `cache_creation_tokens`/`cache_read_tokens` in `ListRuns`) would still pass every existing test while silently corrupting token output on `horde list`. This is the column-order data-corruption risk the brief calls out. Why: `TestNewSQLiteStore_CorrectColumns` sorts both column lists before comparing (sqlite_test.go 205-208), so it pins the SET of columns, not their order, and never touches the SELECT statements at all — it cannot catch a SELECT/scan order mismatch. Suggested fix: set distinct, non-zero `Tokens` on at least one run in a list-path conformance case (e.g. `ListByRepo/FiltersAndOrder` or a new `ListRuns/TokensRoundTrip`) and assert the returned `*Tokens` field-by-field, so all four list SELECTs are covered for both stores.

## WARNING
- [cmd/horde/jsonv1.go:213 `resultsTokens`] The run-result.json FALLBACK branch (the `result.Total*Tokens` deref path, used by `fullResultsToV1`) has no unit test. `fullResultsToV1`/`partialResultsToV1`/`resultsTokens` are absent from `cmd/horde/jsonv1_test.go` (only `statusToV1` and `listToV1` are tested). A regression in the fallback (wrong field mapping, or failing to honor `run.Tokens` precedence over the result fields) would surface wrong token counts on `horde results --json` for runs whose store row predates token persistence but whose run-result.json carries the forward fields. Suggested fix: add a table test for `resultsTokens` covering (a) `run.Tokens` set → stored values win, (b) `run.Tokens` nil + result fields set → fallback values, (c) both nil → nil.
- [cmd/horde/main.go:1365 `fetchLiveTelemetry`] The Docker lazy-live telemetry reader has no unit test. It is new code that sums `phases[].turns`, gates `cost`/`tokens` on all-zero, and returns nil on `InstanceID==""` / unmarshal error. The all-zero-tokens-but-nonzero-cost (and vice versa) gating and the turns-summing are easy to get wrong and would ship wrong live `status`/`list` token values silently. The integration test `TestTokenTelemetrySurfaces` only exercises the finalized (stored) path and only asserts the keys are present (zero values), not this live reader. Suggested fix: a unit test feeding representative costs.json bytes through the parse/sum/gate logic (extract the JSON-to-TokenUsage step so it is callable without a live container, mirroring `tokenUsageFromCostsJSON`).

## NOTE
- [internal/provider/docker_test.go:2483 `TestReadTokenUsage_Missing`] The MALFORMED-JSON path of `ReadTokenUsage`/`tokenUsageFromCostsJSON` (returns nil on bad JSON) is not covered — only "files absent" is. Low risk (the function is best-effort and falls through to run-result.json then nil), but a costs.json that exists-but-is-truncated is the realistic failure mode and isn't pinned. Consider one case writing invalid JSON to costs.json and asserting fallback/nil.
- [internal/provider/docker_test.go:1494] Docker `Finalize` token population is tested only for the StateRunning+marker branch (`TestDockerProvider_Finalize_RunningWithMarkerAndCost`). The timeout, StateStopped, and StateUnknown branches each also call `run.Tokens = ReadTokenUsage(...)` (docker.go 715, 764, 817) but none assert `run.Tokens` afterward. Since all four delegate to the same `ReadTokenUsage` helper (which IS unit-tested) the regression surface is small, but a dropped/duplicated assignment in one branch would not be caught.
- [internal/bootstrap/templates/stack.yaml.tmpl:681 `fetch_token_usage`] The Python status lambda's token extraction has no behavioral test, and `TestRender_StatusLambdaPython` (template_test.go:554) was NOT extended to assert the new token substrings (`fetch_token_usage`, `input_tokens`, `cache_creation_tokens`, etc.) are present in the rendered ZipFile — it still only checks `total_cost_usd`. The cross-language attribute-name contract (Go store consts ↔ TS lambda ↔ Python lambda) is therefore unpinned on the Python side; a misspelled attribute name (e.g. `cache_creation_token`) would ship silently. `TestRender_CfnLint` only lints YAML (and skips when cfn-lint is absent), so it does not exercise the Python logic or attribute spelling. This matches the pre-existing pattern for `fetch_total_cost` (also untested), but extending `TestRender_StatusLambdaPython` with the five new attribute names would cheaply close the gap.
- [cdk/src/status-lambda/index.test.ts:311] TS lambda token coverage is good — both costs.json-present (asserts all five `:it`/`:ot`/`:cct`/`:crt`/`:tn` values incl. summed turns=5) and costs.json-missing (asserts `#it`/`#tn` omitted from the UpdateExpression) are covered with real values. No gap.
- Store conformance backward-compat is well covered: `CreateGetRun/NilOptionalFields` (line 426) and `UpdateRun/SingleField` (line 569) assert old-row/old-item → `Tokens == nil` for BOTH SQLite and DynamoDB via the shared suite. The Dynamo defensive per-attribute parse (`parseTokenAttr`) "any present → non-nil" behavior is exercised by the all-fields case but a partial-attributes item (some token attrs present, others absent) is not specifically tested — acceptable since CreateRun/UpdateRun always write all five together.
